# 模块依赖保护机制

本文档介绍 AET (Agentic Engineering Team) 的模块依赖保护机制，通过"围栏"（Fence）概念确保开发过程中不破坏既定的模块依赖关系。

## 概述

AET 的模块依赖保护机制旨在：

- **防止意外修改**：明确标记禁止修改的模块，避免引入潜在的依赖破坏
- **保持架构完整**：确保模块边界和依赖关系在开发过程中保持一致
- **可追溯的变更**：通过围栏配置记录允许和禁止的修改范围

## 模块依赖结构

AET 在项目分析阶段会生成完整的模块依赖文档，位于项目根目录：

## 围栏机制

### 什么是围栏

围栏（Fence）是 AET 在设计文档中定义的修改边界配置，明确指定：

- **允许修改**：本次开发可以修改的文件和模块
- **禁止修改**：本次开发不能修改的文件和模块
- **条件修改**：在特定条件下才能修改

### 围栏符号

| 符号 | 含义 | 说明 |
|------|------|------|
| ✅ | 允许修改 | 明确列出的可修改文件，可以完整修改 |
| ❌ | 禁止修改 | 明确列出的不可修改文件，任何修改都不允许 |
| 🔵 | 条件修改 | 在特定条件下才能修改 |

### 围栏配置示例

```
✅ 允许修改：
  - src/lib/judge.ts（增加关键动作提取逻辑）
  - src/components/Dashboard.tsx（区分展示关键动作和关键观点）
  - src/prompts/*.ts（如需新增 prompt）

❌ 禁止修改：
  - src/lib/flow-parser.ts（仅复用，不修改）
  - src/lib/prisma.ts（数据库层不变）
  - src/app/api/*（接口层不变）
  - M003-Skill、M004-Auth 模块

🔵 条件修改：
  - src/lib/utils.ts（仅在添加日志功能时可以修改）
```

## 开发流程中的保护机制

### 围栏保护点

围栏保护在以下三个关键点发挥作用：

```
需求分析 → 需求设计 → 开发计划
                           │
                    ┌──────▼──────┐
                    │  围栏点 1    │ ← 生成围栏配置
                    │ 围栏定义     │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   编码实现   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  围栏点 2    │ ← 自检与验证
                    │ 开发者自检   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   PR 创建   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  围栏点 3    │ ← PR 创建前检查
                    │ 最终检查     │
                    └──────┬──────┘
                           │
                      ┌────▼────┐
                      │ 合并    │
                      └─────────┘
```

| 保护点 | 位置 | 保护内容 |
|--------|------|----------|
| 围栏点 1 | 开发计划生成时 | 定义允许/禁止修改的文件范围，形成围栏配置 |
| 围栏点 2 | 编码自检时 | 开发者对照围栏配置检查自己的修改是否越界 |
| 围栏点 3 | PR 创建前 | 提交前最后一次检查，确保没有越界修改 |

## 模块依赖保护规则

### 规则一：禁止反向依赖

高层模块不能依赖低层模块

```
❌ 错误示例：
  - UI 层直接调用 Core 层（绕过 API 层）
  - 业务层直接操作数据库（绕过数据访问层）
```

### 规则二：禁止跨层调用

只能相邻层次之间调用

```
✅ 正确：UI → API → Evaluation → Core
❌ 错误：UI → Evaluation（跨过 API）
```

### 规则三：禁止模块循环依赖

模块之间不能形成循环依赖

```
❌ 错误：
  - Module A → Module B → Module C → Module A
```

### 规则四：保持接口稳定

被多个模块依赖的接口不能随意变更

```
❌ 错误：修改被广泛使用的函数签名，导致调用方全部报错
✅ 正确：新增函数，保留旧函数（可选废弃）
```

## 围栏突破流程

当技术原因必须突破围栏时，应遵循以下流程：

```
技术原因导致必须突破围栏
           │
           ▼
说明原因申请放行
           │
           ▼
    ┌──────────────┐
    │   人工审批    │
    └───────┬──────┘
            │
      ┌─────┴─────┐
      ▼           ▼
    拒绝         批准
      │           │
      ▼           ▼
  寻找替代    记录突破原因
  方案         │
              ▼
        同步更新围栏配置
              │
              ▼
           继续开发
```

### 突破围栏时的操作

1. **说明原因**：详细描述为什么必须突破围栏
2. **申请审批**：提交给人工审批节点
3. **记录原因**：将突破原因写入提交信息
4. **更新配置**：同步更新围栏配置文件

## 最佳实践

### 设计阶段

1. **充分调研**：设计前先确认评估结果展示的具体文件
2. **评估复杂度**：确认"复用"是否需要代码修改
3. **明确边界**：清晰定义允许和禁止修改的范围
4. **接口检查**：确认现有函数返回值是否满足需求

### 开发阶段

1. **遵循围栏**：严格按照围栏配置进行开发
2. **自检自查**：编码完成后对照围栏检查修改文件
3. **记录变更**：如实记录实际修改的内容
4. **及时沟通**：遇到必须突破围栏的情况，及时申请

### 评审阶段

1. **围栏检查**：PR 创建前检查是否越界
2. **变更对比**：对比实际修改与围栏配置的差异
3. **影响评估**：评估越界修改对其他模块的影响

## 常见问题

### Q: 为什么 flow-parser.ts 被禁止修改但实际必须修改？

**A**: 设计阶段低估了集成复杂度。例如初始实现使用动态 `require()`，但运行时出现 ESM/CommonJS 兼容性问题，导致必须修改导入方式。这种情况应通过围栏突破流程处理。

### Q: 如何处理"只读扩展"的需求？

**A**: 对于需要扩展但不能修改逻辑的情况，可以使用以下模式：
- 添加新函数，保留原函数
- 添加新字段，不修改现有字段
- 使用装饰器或中间层隔离变更

### Q: 围栏检查是自动还是人工？

**A**: 当前版本依赖人工检查。理想情况是实现自动化围栏检查，自动扫描修改文件并与围栏配置比对。

## 总结

| 维度 | 现状 | 目标 |
|------|------|------|
| 围栏定义 | 文档级（文本描述） | 结构化（配置文件） |
| 围栏检查 | 人工检查 | 自动化检查 |
| 围栏类型 | 允许/禁止/条件三种 | 多种语义（只读、有限、条件） |
| 突破流程 | 无正式流程 | 审批-记录-同步 |
| 设计准确性 | 部分偏差 | 减少偏差 |

AET 的模块依赖保护机制在设计阶段提供了清晰的边界定义，但在实施阶段的自动化检查和动态调整方面仍有改进空间。通过增强围栏配置语义、建立自动化检查机制和完善围栏突破流程，可以进一步提升依赖保护的可靠性。
