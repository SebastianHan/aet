# 工作流说明

本文档详细介绍 AET 的完整工作流程、各阶段详情以及关键概念。

## 整体工作流程

AET 通过多智能体协作完成从需求到实现的完整开发流程：

```
用户输入 Issue URL
        │
        ▼
┌─────────────────┐
│   Aet-Router    │ ← 路由智能体：认领 Feature，检查 Checkpoint
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Aet-Design    │ ← 设计智能体：RAS → RDS → SDD → 评审
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Aet-Implementation │ ← 实现智能体：TDD 任务执行
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Aet-Test      │ ← 测试智能体：功能验证、需求追溯
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Aet-Delivery  │ ← 交付智能体：PR 质量检查 → 提交 PR
└────────┬────────┘
         │
         ▼
      PR 创建
```

## 各阶段详细说明

### 1. 路由阶段 (Aet-Router)

**职责**：理解用户需求，认领 Feature，路由到合适的工作流

**执行步骤**：

1. **解析输入**：提取 Issue URL 或需求描述
2. **认领 Feature**：
   - 检查 Issue 是否已被认领
   - 创建特性分支
   - 更新 Issue 状态
3. **Checkpoint 检测**：
   - 检查是否存在已中断的进度
   - 询问用户继续还是重新开始
4. **意图识别**：
   - 实现需求 → 设计-实现流程
   - Bug 修复 → Bugfix 流程
   - 其他 → 相应处理

**Checkpoint 文件**：`.aet/features/{feature-name}/checkout.json`

---

### 2. 设计阶段 (Aet-Design)

**职责**：将需求转化为详细的设计文档

**执行步骤**：

| 步骤 | 子步骤 | 输出 | 用户确认 |
|------|--------|------|----------|
| 1 | 需求分析 | RAS 文档 | 需求分析评审 |
| 2 | 需求评审 | 通过/不通过 | ✓ |
| 3 | 需求设计 | RDS 文档 | 需求设计评审 |
| 4 | 需求设计评审 | 通过/不通过 | ✓ |
| 5 | 开发计划 | SDD 文档 | 开发计划评审 |
| 6 | 开发计划评审 | 通过/不通过 | ✓ |
| 7 | 提交文档 | Git 提交 | - |

**输出文档**：

| 文档 | 全称 | 说明 |
|------|------|------|
| **RAS** | Requirements Analysis Specification | 需求分析规范 |
| **RDS** | Requirements Design Specification | 需求设计规范 |
| **SDD** | Software Design Document | 软件设计文档 |

**输出位置**：`.aet/features/{feature-name}/design/`

---

### 3. 实现阶段 (Aet-Implementation)

**职责**：基于设计文档执行 TDD 开发

**TDD 循环**：

```
红：写失败测试 → 绿：写最简代码 → 重构：优化代码 → 循环
```

**执行步骤**：

1. 读取设计文档和 SDD
2. 对每个任务（checkbox）：
   - 编写失败的测试
   - 运行测试验证失败
   - 编写最简代码
   - 运行测试验证通过
   - 提交代码
3. 标记任务完成
4. 围栏检查

**围栏配置**：

| 符号 | 含义 |
|------|------|
| ✅ | 允许修改 - 本次开发可以修改的文件 |
| ❌ | 禁止修改 - 不应该修改的文件（除非申请突破） |
| 🔵 | 条件修改 - 满足特定条件才能修改 |

**输出位置**：`.aet/features/{feature-name}/implementation/`

---

### 4. 验证阶段 (Aet-Test)

**职责**：验证实现是否符合设计要求和功能需求

**执行步骤**：

1. **功能验证**：
   - 检查所有必需功能是否已实现
   - 验证接口是否符合设计
2. **需求追溯**：
   - 将每个需求映射到实现代码
   - 识别未实现的需求
3. **测试覆盖**：
   - 检查测试用例是否充分
   - 验证边界条件覆盖
4. **生成报告**：
   - 输出验证结果
   - 列出未完成项

**输出位置**：`.aet/features/{feature-name}/verification/`

---

### 5. 交付阶段 (Aet-Delivery)

**职责**：PR 创建和后续处理

**执行步骤**：

1. **质量检查**：
   - 运行 lint 检查
   - 确保所有测试通过
   - 检查代码覆盖率
   - 验证与目标分支无冲突
2. **用户确认**：
   - 询问是否提交 PR
   - 显示 PR 预览
3. **PR 创建**：
   - 使用 `feature-management` 创建 Pull Request
   - 自动填写 PR 描述
4. **后续处理**：
   - 报告 PR 链接
   - 等待 Review 反馈

## PRD 工作流

当用户使用 `/aet:prd` 命令时，AET 执行以下流程：

### PRD 生成模式（默认）

通过 aet-prd agent 协调 6 阶段 PRD 生成流程：

```
用户输入需求描述
        │
        ▼
┌─────────────────┐
│  1. 产品分析    │ ← aet-analyzing-prd
└────────┬────────┘
         │ 评审通过
         ▼
┌─────────────────┐
│  2. 竞品研究    │ ← aet-researching-prd-competitor
└────────┬────────┘
         │ 评审通过
         ▼
┌─────────────────┐
│  3. 创新分析    │ ← aet-analyzing-prd-innovation
└────────┬────────┘
         │ 评审通过
         ▼
┌─────────────────┐
│  4. PRD 撰写    │ ← aet-writing-prd（含 UX 设计）
│     UX 设计     │
└────────┬────────┘
         │ 评审通过
         ▼
┌─────────────────┐
│  5. 原型构建    │ ← aet-building-prd-prototype
└────────┬────────┘
         │ 评审通过
         ▼
┌─────────────────┐
│  6. 终审交付    │ ← 并行生成报告、Features、幻灯片
└────────┬────────┘
         │
         ▼
   PRD 产物交付
```

### FR 开发批处理模式

当使用 `/aet:prd dev` 时，执行 FR 批量开发流程：

```
扫描 .aet/prd/features/
        │
        ▼
┌─────────────────┐
│ 筛选未处理 FR   │ 状态为"新增"或"部分已实现"
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 循环：展示 FR  │
│ 征求用户确认   │
└────────┬────────┘
         │
    ┌────┴────┐
    │ 确认开发 │
    └────┬────┘
         │
         ▼
┌─────────────────┐
│ 创建 Feature    │ 创建 .aet/features/{feature-name}/
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 转接开发流程    │ 调用 workflow_start
└─────────────────┘
```

### PRD 产物验证清单

| 任务 | 必需产物 | 验证路径 |
|------|----------|----------|
| 终审报告 | 终审报告 | `.aet/prd/review/final-review.md` |
| Features | Feature 文件 | `.aet/prd/features/FR00X-*.md` |
| 产物清单 | 产物清单 | `.aet/prd/artifact-manifest.md` |
| 创新报告 | 技术创新报告 | `.aet/prd/reports/innovation-report.md` |
| 幻灯片 | HTML 幻灯片 | `.aet/prd/reports/innovation-report-slides.html` |
| 产品介绍 | 产品概览 | `.aet/prd/reports/产品介绍.md` |
| 技术架构 | 技术方案 | `.aet/prd/reports/技术架构.md` |
| 用户手册 | 使用指南 | `.aet/prd/reports/用户手册.md` |

## 人工确认点

AET 在关键节点会暂停等待用户确认：

| 节点 | 询问内容 |
|------|----------|
| **设计评审前** | 需求分析已完成，是否继续设计评审？ |
| **实现前** | 开发计划已生成，是否开始实现？ |
| **PR 提交前** | PR 已创建，是否提交？ |

## SR-AR 需求分解

AET 采用 SR-AR 方法进行需求分解：

### SR (System Requirement)

系统需求，对应一个主要场景或功能域：

- 数量控制：一般 1-2 个
- 一个 SR 对应一个功能域
- 优先合并，避免过多 SR

### AR (Architecture Requirement)

架构需求，属于某个具体系统元素：

- 一对一原则：一个 AR 属于一个模块
- 数量控制：每个 SR 默认 1-2 个 AR，最多 3 个
- 必须列出能力点

### 分解示例

```
SR-1: 用户认证功能
  ├── AR-1.1: 用户登录（登录模块）
  └── AR-1.2: 用户注册（注册模块）

SR-2: 内容管理
  ├── AR-2.1: 内容创建（内容模块）
  └── AR-2.2: 内容审核（审核模块）
```

## 项目结构

AET 在项目中创建以下目录结构：

```
.
├── .aet/
│   ├── config.json          # 项目配置
│   ├── features/
│   │   └── feature-{name}/
│   │       ├── feature.json      # Feature 元数据
│   │       ├── issue.md          # Issue 内容副本
│   │       ├── checkout.json      # Checkpoint 快照
│   │       ├── requirements/     # 需求文档
│   │       ├── design/           # 设计文档
│   │       │   ├── *-ras.md     # 需求分析规范
│   │       │   ├── *-rds.md     # 需求设计规范
│   │       │   └── *-sdd.md     # 软件设计文档
│   │       ├── implementation/   # 实现文档
│   │       │   └── *-plan.md    # 实现计划
│   │       ├── verification/     # 验证报告
│   │       └── tests/            # 测试代码
│   ├── project-analysis/        # 项目分析输出
│   └── {task-id}/                # 非 Feature 任务输出
└── visualization/            # 看板仪表盘
```
