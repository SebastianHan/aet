# Agent 需求设计检查表

本检查表用于评审 Agent 需求设计说明书的质量。检查项直接对应模板 `assets/agent-requirements-design-template.md` 的结构，并强调 **任意 AtomGit issue + 目标仓库真实结构** 下的载体决策、契约边界、风险控制与验证完整性。

---

## §1 概要

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 名称是否明确 | ERROR | 能识别本次 Agent / capability，不与其他文档混淆 |
| 描述是否清晰 | WARNING | 一句话能说明“做什么 + 为何需要” |
| 需求来源是否可追溯 | ERROR | 必须能追溯到 AtomGit issue / issue 摘要 / requirements analysis |
| 设计结论是否填写 | ERROR | 明确是新 agent、扩已有 agent、agent suite extension、agent runtime + companion surfaces 的 mixed 方案 |

---

## §2 Issue 与仓库基线

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| Issue 摘要是否具体 | ERROR | 明确问题背景、目标能力、验收重点，而非泛泛“提升效率” |
| 仓库上下文是否真实 | ERROR | 至少识别相关模块、目录、docs、tests、入口或执行器 |
| 载体语义是否明确 | ERROR | `agents/` / `commands/` / `skills/` 是平台定义、提示词载体还是语言模块，必须说清楚 |
| 是否区分事实与假设 | ERROR | 若只有 web 上下文，暂定文件落点和未确认假设必须显式标注 |
| 上下游关系是否说明 | WARNING | 输入来源、输出消费者、关键依赖是否清楚 |

---

## §3 设计结论摘要

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 用户价值是否可验证 | WARNING | 能说清减少什么成本、避免什么错误或提升什么效果 |
| 成功标准是否可观察 | ERROR | 有可执行或可观察的成功判定 |
| 设计结论是否回答 carrier 选择 | ERROR | 回答“落在哪些载体上”以及“为什么不是其他方案” |
| 是否给出 Agent 产品面结论 | ERROR | 若目标是开发 Agent 套件，需说明 runtime agent、prompt、skill、command、adapter、install/docs、verification 哪些在范围内 |

---

## §4 载体决策与边界

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| Carrier 决策是否逐类说明 | ERROR | `agents/`、prompts、`skills/`、`src/`、`commands/`、platform adapters（如 `.opencode/` / `.codex/` / `.claude-plugin/`）、agent registration / config、docs / tests 中相关项已判断 |
| 是否显式说明不选方案原因 | WARNING | 说明为什么不新增独立 agent，或为什么不只改 module / command |
| 允许 / 禁止修改边界是否明确 | ERROR | 路径与原因清晰，避免“修改相关文件” |
| 是否避免隐式扩 scope | ERROR | 无未声明的新增载体或改动范围 |
| 是否避免不完整缩 scope | ERROR | 若需求本质上是交付 Agent 套件，不能只设计其中一层而遗漏命令入口、适配器暴露、安装发现或验证证据 |
| 是否避免语言幻觉 | ERROR | 不能因为仓库使用 Python / Node 就把 `agents/` / `commands/` / `skills/` 默认写成语言 package |
| 是否避免过早实现化 | ERROR | 需求设计阶段不得无依据展开到 `__init__.py`、`agent.py`、`skill.py`、CLI 模块或包管理文件 |

---

## §5 领域模型与能力分解

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 输入输出契约是否明确 | ERROR | 输入从哪里来、由谁消费、字段 / 语义 / 前置条件是什么 |
| 能力分解是否可追溯 | ERROR | 每个能力有触发条件、逻辑、输出、owner carrier |
| 是否覆盖关键控制点 | ERROR | 审批、审计、回滚、幂等、重试等关键能力未遗漏 |
| 是否避免能力职责重叠 | WARNING | 相邻能力边界清晰 |

---

## §6 端到端流程与状态机

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 主流程是否完整 | ERROR | 输入 → 上下文建立 → 核心判断 / 执行 → 可选审批 / 恢复 → 输出 / 交接 |
| Mermaid 状态图是否可渲染 | WARNING | 语法正确，节点关系清晰 |
| 状态节点是否定义进入 / 退出条件 | ERROR | 每个关键状态都有 entry / output / exit |
| 控制点是否被建模 | ERROR | 审批、拒绝、恢复、重试、重复触发不能只是一句注释 |
| 非 happy path 是否明确 | ERROR | 权限不足、执行失败、输入异常、目标不存在等路径有说明 |

---

## §7 安全策略、审计与可观测性

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 风险分级 / 审批是否按需说明 | ERROR | 涉及副作用或高风险执行时必须设计控制策略 |
| 回滚 / 补偿是否具体 | ERROR | 不是“失败时提示重试”这类空话 |
| 审计 / 日志 / 指标是否明确 | WARNING | 至少说明需要什么证据来证明执行和结果 |

---

## §8 仓库产物变更计划

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 产物列表是否完整 | ERROR | 至少覆盖实际受影响的模块 / config / docs / tests / scripts / prompts / adapter manifests / bootstrap / install docs |
| 动作是否明确 | ERROR | 新增 / 修改 / 不涉及 / 暂定清晰 |
| 产物格式与消费方是否明确 | ERROR | 需说明产物是 Markdown / SKILL.md / YAML / JSON / JS / Python / other，以及谁来识别它 |
| 产品面归属是否清楚 | ERROR | 每个产物应能对应到 agent runtime / prompt / skill / command / adapter / install-doc / verification 等交付层 |
| 是否停留在正确抽象层级 | ERROR | 若 exact file path 未被 live repo 或平台约定证明，应优先写 artifact family / anchor，而不是臆造实现文件树 |
| 变更原因是否可解释 | WARNING | 能追溯到设计结论和仓库现状 |

---

## §9 集成点与契约

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 上游输入契约是否明确 | ERROR | 输入来源、格式、消费方、前置条件清楚 |
| 内部模块契约是否明确 | ERROR | 提供方、消费方、契约内容、兼容性说明完整 |
| 平台适配 / 共享运行时集成是否定义 | ERROR | 平台适配层、共享 runtime、registration loader、必要外部依赖等集成方式明确 |

---

## §10 验证与验收场景

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 是否覆盖正常路径 | ERROR | 至少一个 happy path |
| 是否覆盖关键控制路径 | ERROR | 至少一个 approval / review / recovery / rollback 路径 |
| 平台适配路径是否覆盖 | ERROR | 若仓库存在适配层，至少说明一个 discovery / load / install / invoke 路径 |
| 是否覆盖异常路径 | ERROR | 至少一个失败 / 边界场景 |
| 场景步骤与结果是否可验证 | WARNING | 不应是抽象描述 |

---

## §11 非目标、开放问题与交接说明

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 非目标是否明确 | WARNING | 能阻止 scope creep |
| 开放问题是否标注影响与建议 | INFO | 悬而未决项有处理建议 |
| 交接说明是否可供下游使用 | WARNING | 下游计划阶段能直接知道哪些是已定、哪些待确认 |

---

## 文档格式检查

| 检查项 | 严重程度 | 检查要点 |
| -------- | ---------- | ---------- |
| 是否保留模板结构 | ERROR | 结构不应被随意破坏 |
| instruction 注释是否移除 | ERROR | 最终文档不应输出 instruction 注释 |
| Mermaid 图表是否正确 | WARNING | 可渲染 |
| 是否混入实现代码 | ERROR | 设计文档应聚焦设计与契约，禁止夹带实现代码 |
| 是否夹带实现脚手架 | ERROR | 设计文档不应无依据给出包结构、类名、实现文件名 |
