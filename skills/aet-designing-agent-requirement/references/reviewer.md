# Agent 需求设计 Reviewer 方法指南

本文档定义 Agent 需求设计说明书的评审方法。该类文档的目标不是“画一个漂亮方案”，而是基于 **AtomGit issue + 目标仓库真实结构**，做出正确的 carrier 决策、流程设计、契约划分与风险控制判断。

## 评审重点

1. **Issue 与仓库事实优先**：优先检查文档是否基于 issue 原文、仓库真实文件与已有能力，而不是抽象想象。
2. **Carrier 决策清晰**：重点判断为什么落在 agent runtime / prompts / companion skills / commands / runtime modules / registration-config / platform adapters，而不是别的地方。
3. **Carrier 语义正确**：重点判断 `agents/` / `commands/` / `skills/` 是平台识别的定义载体，还是运行时代码目录；不要把两者混为一谈。
4. **产品面完整**：如果用户要的是“开发 Agent / 一套 agent 能力”，重点判断文档是否覆盖 runtime agent、prompt、skill、command、adapter、install / discovery、verification 这些真正影响可交付性的层。
5. **抽象层级正确**：需求设计应给出能力边界、carrier 家族、格式与消费方，而不是抢跑到实现文件树或包结构。
6. **控制点完整**：审批、恢复、回滚、审计、重试、幂等都应是正式系统行为，而不是一句“后续补”。
7. **失败与边界明确**：中断、重试、重复触发、执行失败、权限不足是否有清晰处理。
8. **交接可落地**：设计完成后，后续开发计划或实现阶段是否可以据此直接拆任务。
9. **平台适配层不遗漏**：如果仓库通过 `.opencode/`、`.codex/`、`.claude-plugin/` 或其他适配器暴露能力，文档是否明确说明要不要改、为什么改、如何验证。

## 评审流程

### [1] 确定评审对象

```text
评审文档: {document-path}
对应检查表: agent-requirements-design-review-checklist.md
```

### [2] 做 issue / repo 对照评审

至少对照以下事实来源：

- AtomGit issue 页面或 issue 摘要
- 仓库 README / docs / analysis 页面
- 本地代码仓中的相关模块、入口、执行器、配置、测试
- 设计文档中引用的现有能力与边界

如果文档没有体现这些事实，或与实际代码冲突，应判为 **ERROR**。

### [3] 执行逐项检查

评审时请特别关注以下问题：

- 文档是否清楚说明“为什么是这个 carrier 组合”？
- 如果需求本质上是交付一整套 agent 能力，文档是否说明各交付层之间的关系，而不是只描述 `agents/` 或只描述某个 prompt / skill？
- 是否把“新增 Agent”偷换成“默认新增 `agents/{name}` 目录”？
- 是否把平台识别的 `agents/` / `commands/` / `skills/` 误写成 Python / TypeScript package？
- 是否在需求分析阶段就抢跑到了 `__init__.py`、`agent.py`、`skill.py`、CLI 模块、包管理文件等实现脚手架？
- 是否遗漏了隐藏目录中的平台适配层（如 `.opencode/`、`.codex/`、`.claude-plugin/`）？
- 是否覆盖了上游输入、下游输出、关键契约与控制点？
- 是否把 Agent 设计误扩成了无关的通用非 Agent 方案？
- 是否存在隐式扩 scope、模糊路径或未经证实的文件落点？

## 严重程度分类

### ERROR（必须修复）

出现以下任一情况通常应判为 ERROR：

- 没有基于真实 issue / 仓库文件做设计判断
- carrier 决策缺失或不自洽
- 主流程或关键控制路径缺失
- 对高风险执行没有审批 / 回滚 / 审计设计
- 产物变更计划模糊，无法指导后续开发

### WARNING（建议修复）

- 说明不够具体，但主结论可理解
- 边界说明不足，但未造成明显歧义
- 验收场景或证据策略不够充分

### INFO（可选优化）

- 可以补更多仓库引用证据
- Mermaid 图或术语解释可更清晰
- 可补充未来扩展建议

## 评分标准

| 分数 | 描述 | 结论 |
| ------ | ------ | ------ |
| 90-100 | 仓库事实充分、carrier 决策清晰、流程闭环完整 | ✅ 通过 |
| 75-89 | 结论基本可用，但仍需针对性修正 | ⚠️ 条件通过 |
| 0-74 | 关键判断缺失或与仓库现状不符 | ❌ 不通过 |

**评分计算方法**：

```text
基础分 = 100
扣分 = ERROR × 10 + WARNING × 3 + INFO × 1
最终分 = max(0, 基础分 - 扣分)
```

## 建议输出格式

评审结论建议按以下结构给出：

```markdown
## 评审结论
- 结论：通过 / 条件通过 / 不通过
- 得分：XX

## 关键问题
1. [问题]
   - 严重程度：ERROR / WARNING / INFO
   - 证据：[...] 
   - 建议：...

## 总体建议
- [下一步建议]
```
