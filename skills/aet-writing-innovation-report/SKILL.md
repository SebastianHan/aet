# 技术创新报告撰写指南

## 报告定位

本 skill 用于撰写系统性的技术创新分析报告，帮助评估技术路线、创新机制、壁垒与可行性。  
报告适用于技术决策、方案评审、产品早期验证与研发沟通场景。

## 最高优先级规则

1. **技术创新主导**：报告必须围绕技术问题与技术方案展开，不得以市场/创业叙事为主
2. **市场最小支撑**：允许出现市场/竞品信息，但仅用于支撑技术判断，且默认集中放在第 2 章背景中
3. **证据化表达**：关键结论应给出来源依据（前序阶段产物、竞品事实、可验证指标）
4. **禁止泛商业化**：禁止把大量篇幅用于融资、增长、营销、商业计划书风格内容
5. **结构固定**：必须按本文件定义的 **7 章正文**输出；**图文并茂与论证形式**为贯穿全文的硬性要求（下文称「第 8 条呈现约束」），不单列成章，不得随意改序或合并为泛化章节

## 报告固定结构（必须按顺序）

```
1. 整体创新方案名称（首页）
2. 背景描述：当前技术方案所针对的现实应用背景、需求、痛点（含最小必要市场支撑）
3. 业界现有技术方案：相关方案描述 → 各方案的问题场景、局限性与不足
4. 本项目创新方案整体描述：解决的痛点、差异化创新点、可能应用场景、产品形态
5. 技术方案展开：各步骤的动机、本步痛点、技术挑战、与业界差异、关键技术点与产出（每步独立成段，字段见下文）
6. 技术方案预期效果：可验证的预期效果与量化表达
7. 技术壁垒、可绕过性与技术点取证方法（含第三方使用时的取证路径与证据链）

第 8 条（呈现约束，贯穿 1–7，不单成章）：
适当使用对比表格、架构图、场景图等，使全文图文并茂、逻辑严谨；禁止无说明的装饰性图表。
```

## 章节写作要求（逐章）

### 1) 整体创新方案名称（首页）
- 使用稳定名称：优先 `innovationSolutionName`，其次 `productName`
- **主视觉为愿景关键词**：提炼 3–6 个短词或短语（可从 `valueProposition`、`realNeeds`、创新目标归纳；禁止无依据编造具体数字，允许基于前序产物的合理提炼）；方案名称作为标题或副标题
- **一句话技术定位**仅作次要信息（小字号段落或脚注），详细技术表述放在第 4/5 章
- 版本/日期等元信息可保留
- 本章可配极简图示（可选）：如问题域示意图，须与第 2 章论证衔接

### 2) 背景描述
- 必须覆盖：**当前拟采用的技术方案所针对**的现实应用背景、真实需求与约束、痛点问题（写清「为谁、在什么条件下、为何痛」）
- **数据溯源（硬性）**：凡出现数值、比例、规模、时间、成本、市占等量化表述，必须标注**数据来源**（机构/报告名/数据集/论文/统计口径与日期）；若为内部测算须标注「内部估算」并简述假设与局限。**禁止**无来源的裸数字
- 建议引用：`problemStatement`、`needsAssessment.realNeeds`
- 输出要求：显式回答「为什么现在必须解决该问题」以及问题边界（与非目标、排除范围可对齐 PRD/分析产物）
- 最小市场分析放在本章完成：仅保留需求强度、目标场景规模级别、采用驱动因素等**支撑技术判断**的必要信息
- 约束：后续章节不再展开市场叙事，只在需要时引用本章结论

### 3) 业界现有技术方案
- 写作顺序：**先**概括与本问题域相关的业界技术路线或代表方案；**再分方案**展开
- 每个业界方案须写清：方案描述（机制/架构要点）、典型**问题场景**（何时好用/何时失效）、**局限性与不足**（与第 2 章痛点对照）
- 建议引用：`competitors[].techStack/coreMechanisms/performanceCostNotes/weaknesses`
- 必须包含至少一张业界方案对比表（Markdown 表格），维度建议含架构/性能或成本/可扩展性/运维或安全等中的至少三项

### 4) 本项目创新方案整体描述
- 必须覆盖：针对第 2 章痛点的**解决关系**、**差异化创新点**（与第 3 章逐条对照）、可能的应用场景、产品形态（边界、交付形态、与原型/PRD 一致）
- 建议引用：`coreDifferentiation`、`inScope`、`coreFeatures[].userScenarios`、产品形态字段
- 必须解释「与业界方案相比为何不同、为何可成立」

### 5) 技术方案展开
- 必须采用**步骤化**表达；**每一步单独成小节（或小标题）**，不得把多步合并成一段而省略下列任一项：
  - `step`（步骤名称）
  - `motivation`（在整体链路中为何需要该步）
  - `painAddressed`（**本步**直接对应的痛点，可指回第 2 章）
  - `keyProblem`（**本步**的技术挑战/攻关点）
  - `differentiationVsIncumbent`（**本步**相对业界/现有主流做法的差异，可指回第 3 章）
  - `keyTechPoint`（关键技术决策或机制）
  - `expectedOutput`（该步可交付/可验证的产出）
- 分工说明：`motivation` 写「为何要有这一步」；`painAddressed` 写「这一步缓解哪条痛点」；勿用一句空话同时冒充二者
- 建议引用：`candidateSolutionComparison`、`technicalSolutionPoints`、架构相关字段
- 必须包含至少一张架构图（Mermaid）；复杂交互须配场景图（流程/时序）

### 6) 技术方案预期效果
- 本章对应「技术方案**预期**达到的效果」，必须可验证、可度量
- 建议每个效果维度包含：`baseline`、`target`、`measurementMethod`、`estimatedImpact`
- 建议引用：`validationMetrics`、效果评估字段
- 必须包含至少一张「基线—目标」或「前后」对比表

### 7) 技术壁垒、可绕过性与技术点取证方法
- 必须覆盖：壁垒类型与来源、潜在绕过路径、绕过成本与条件、可行的防御或验证手段
- **壁垒类型约束**：**不得**以「生态构建」「社区规模」「伙伴网络」「开源声量」「运营护城河」等市场与运营叙事作为壁垒主体（与合规背书、客户信任同类，**不算**技术壁垒）；壁垒应写**实现复杂度、机制耦合、数据与状态设计、算法与性能门槛**等可被工程讨论或绕过的维度
- **技术点取证方法（本章必写小节）**：回答「若他人使用了与本创新相关的关键技术，如何从技术事实层面**收集与固定证据**、以**论证**其确实被使用（或高度疑似）」。须包含：
  - **可取证的技术表征**：与本方案关键步骤/关键机制对应的、在第三方产品中**可能被观测**到的特征（接口语义、时序与资源特征、算法侧写、网络与存储痕迹、发布物中的实现线索等），并说明哪些特征**特异性强**、哪些易撞车
  - **取证路径与手段**：在合法与授权前提下可采用的步骤（如对照实验、黑盒行为对比、公开信息聚合、日志与遥测约定等），避免教唆越权访问或破坏计算机系统
  - **证据链组织**：单点证据 → 多源互证 → 与第 5 章技术步骤的**映射关系**；每一类证据注明可信度与**反证可能**（独立实现、配置差异、混淆与伪造）
  - **边界说明**：技术取证能证明到什么粒度、何处需司法鉴定/律师/公证等后续程序（本章只作技术方法论述，不提供法律结论）
- 建议引用：`barrierAndBypassAnalysis`（若 JSON 中已含取证要点则直接展开；否则在本章基于技术方案自行归纳）
- 可与第 6 章验证指标呼应，形成闭环

## 内容融合规则（内部约束，不单独成章）
- 必须确保以下内容已被映射到 2-7 章：
  - 技术挑战 -> 第 2 / 5 章
  - 分步痛点与业界差异（`painAddressed` / `differentiationVsIncumbent`）-> 第 5 章
  - 方案对比 -> 第 3 / 5 章
  - 架构 -> 第 4 / 5 章
  - 验证指标 -> 第 6 / 7 章
  - 技术点取证与举证思路 -> 第 7 章（与壁垒、可绕过性同一章内展开）
- 若某项未映射，视为报告不完整

---

## 第 8 条：图文并茂与逻辑严谨（硬性，贯穿第 1–7 章）

1. 每个核心章节（2-7）至少 1 个可视化元素（对比表格、架构图、场景图、SWOT策略矩阵、雷达图、纵横分析图表六选一或组合）
2. 至少 2 个对比表（业界方案对比、预期效果或基线—目标对比）
3. 至少 1 张架构图（Mermaid）
4. 至少 1 张场景图（流程图、时序图或用户路径/系统交互场景）
5. **第3章必须包含差异化机会雷达图（Mermaid）**，数据来源为`02-competitor-research.json.opportunityRadarAnalysis`，展示各机会点的多维度优先级评估
6. **第3章必须包含纵向演进分析图表**，数据来源为`02-competitor-research.json.competitors[].verticalEvolutionAnalysis`和`02-competitor-research.json.crossVerticalInsightAnalysis`
7. **第7章必须包含SWOT策略矩阵表格**，数据来源为`03-innovation-analysis.json.swotAnalysis`，展示优势-机会、劣势-机会、优势-威胁、劣势-威胁组合策略
8. 每张表、每幅图旁须有短说明，包含「结论 + 依据/数据 + 对论证的作用」，保证图文服务同一逻辑链，而非堆砌

## 使用说明

1. **启动报告撰写**：用户提供产品相关信息后，按本 skill 结构引导用户补充关键信息
2. **信息收集**：从多 Agent 产物汇总并检查信息充分性（方案名、愿景关键词素材、步骤化字段含 `painAddressed`/`differentiationVsIncumbent`、量化数据与来源、量化效果、产品形态）
3. **报告生成**：严格按第 1–7 章结构输出，并落实**第 8 条呈现约束**（章节职责清晰，避免重复）
4. **审核校对**：检查「结构完整、图文配额、证据可追溯、技术内容占比、图表与结论一一对应」是否达标

## 输出路径

报告保存到 `.aet/prd/reports/innovation-report.md`。

幻灯片由编排 Agent 调用 `aet-generating-html-slides` skill 生成，保存到 `.aet/prd/reports/innovation-report-slides.html`。
