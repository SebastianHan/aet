# 设计思维操作手册

## 定位

当用户需求不明确、需要深入用户洞察时使用。设计思维帮助从用户视角定义问题，而非从既有能力出发。

## Double Diamond模型

设计思维遵循Double Diamond框架：先发散探索，后收敛聚焦。

```
发散（探索） → 收敛（定义） → 发散（构思） → 收敛（实现）
```

## 1. 同理心访谈技巧

### 核心原则

1. **不问假设性问题** - 避免"你会想要X吗？"这类假设
2. **聚焦过去行为** - "上次你遇到这种情况是怎么做的？"
3. **倾听80%** - 让用户讲述，适时追问
4. **观察非语言信号** - 语气、停顿、情绪波动

### 访谈结构

1. **开场（5分钟）**
   - 介绍访谈目的
   - 强调没有正确答案
   - 征得录音/记录同意

2. **背景探索（15分钟）**
   - 了解用户角色和场景
   - "请描述一个典型的工作日"
   - "最近一次完成X任务是在什么时候？"

3. **痛点深挖（25分钟）**
   - 使用question-templates.md中的痛点挖掘问题集
   - 追问具体情境和感受
   - "能举个例子吗？"
   - "那件事让你感觉如何？"

4. **收尾（5分钟）**
   - 询问还有什么想补充的
   - 感谢并说明后续沟通方式

### Agent执行要点

- 访谈前准备访谈提纲
- 记录用户的情绪词和高频痛点
- 使用"用户原话"而非"翻译后的话"记录

## 2. 用户旅程地图绘制

### 目的

将用户在完成任务过程中的行为、想法、情绪可视化，识别痛点和机会。

### 模板结构

| 阶段 | 行为 | 想法 | 情绪 | 痛点 | 机会 |
|------|------|------|------|------|------|
| 认知 | 用户如何发现需求 | 用户的理解 | 情绪波动 | 高摩擦点 | 改进空间 |

### 绘制步骤

1. **定义起点和终点**
   - 起点：用户首次意识到需求
   - 终点：需求被满足（或放弃）

2. **拆分阶段**
   - 通常5-8个阶段
   - 每个阶段有明确目标

3. **填写每个阶段的五个维度**
   - 行为：用户实际做了什么
   - 想法：用户在思考什么
   - 情绪：用户感受如何（用emoji或1-5分）
   - 痛点：具体卡点和阻碍
   - 机会：可改进的空间

4. **识别关键时刻**
   - 情绪最低点 → 优先解决
   - 情绪最高点 → 提炼亮点

### 输出

- 完整用户旅程地图
- Top 3痛点清单
- Top 3机会清单

## 3. How Might We问题重构

### 目的

将问题陈述转化为可行动的创意挑战。

### 规则

- "HMW"开头
- 一个问题聚焦一个方面
- 使用正向、积极的语言
- 足够具体但不过度限制

### 操作步骤

1. **从问题陈述出发**

   原始问题：用户在电商平台退货流程太麻烦

2. **多角度重构**

   | 角度 | HMW问题 |
   |------|---------|
   | 简化流程 | HMW让退货流程减少到3步？ |
   | 预防问题 | HMW在购买前就帮助用户做出正确选择？ |
   | 情感关怀 | HMW让用户感觉退货是被理解的而非被惩罚？ |
   | 信息透明 | HMW让用户随时知道退货进度？ |
   | 激励设计 | HMW让用户不需要退货（即一次选对）？ |

3. **选择HMW进入创意阶段**
   - 优先选择影响范围大的
   - 平衡可行性和创新性

### Agent执行要点

- 列出所有HMW变体，不筛选
- 数量目标：至少5-10个HMW
- 按影响力和可行性初步排序

## 4. 利益相关者地图

### 目的

识别所有相关方，理解他们的需求和关系。

### 绘制方法

1. **中心放产品/服务**
2. **内圈：直接用户**
3. **外圈：间接受影响者**
4. **标注关系线**：支持/冲突/依赖

### 考虑的问题

- 谁是决策者？
- 谁是使用者？
- 谁会被变化影响？
- 谁能阻止项目？

## 5. 快速原型方法

### 原型类型选择

| 类型 | 成本 | 用途 | 适用阶段 |
|------|------|------|---------|
| 草图 | 极低 | 概念沟通 | 早期 |
| 纸质原型 | 低 | 流程测试 | 中期 |
| 数字原型 | 中 | 交互体验 | 中后期 |
| 功能原型 | 高 | 实际功能 | 后期 |

### 原型制作原则

- 最小成本：只用必要的元素
- 可抛弃：不要过度投入
- 快速迭代：有问题就改

### 测试后记录

- 用户做了什么
- 用户说了什么
- 卡在哪里
- 亮点是什么

## 使用场景判断

选择design-thinking-guide.md当：
- 用户说"我不知道用户真正想要什么"
- 需求收集阶段，用户反馈模糊
- 需要深入理解用户行为背后的动机
- 产品方向不明确，需要探索

不选择当：
- 需求已明确，只是实现问题
- 时间极其有限，需要快速交付
- 技术限制主导，非用户因素
